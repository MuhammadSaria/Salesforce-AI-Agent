# Providus Nexus Phase 1 Security

Phase 1 is supervised and fail-closed. Salesforce, Jira, model output, CLI output, retrieved metadata, and user messages are untrusted inputs; none authorize commands, broaden scope, approve work, or select an org.

## Identity and approval

Every `/api/*` call requires the middleware bearer credential. Direct chat also requires Apex-produced Salesforce org/user IDs and explicit boolean permission claims. The API re-resolves live same-org registry evidence at planning, validation, approval, and deployment boundaries. Default Salesforce orgs are never used.

`AI_Agent_Admin` permits implementation approval and `AI_Agent_Deploy` permits deployment approval. Implementation approval binds plan version/hash, scope, inspection, actor, and org. A later deployment approval binds the exact successful Salesforce validation and baseline/source/package/commit hashes. Data changes affecting more than ten records require a distinct exact `DATA_OPERATION` approval; approval types are not interchangeable.

## Evidence and source

Inspection evidence carries source org, evidence identity, timestamp, active state, component identity, and canonical inspection hash. Planning and specialists receive only bounded relevant evidence. Ownership is fixed: Object/Field owns CustomField, Security owns PermissionSet, and Flow owns Flow. Canonical paths derive from type/API identity and cannot be selected by the model.

Task 9 validates the complete operation set before any source write: exact scope and operation identity, ownership, size, secret/script rejection, safe bounded XML, root/namespace, Number-field constraints, least privilege, connected recurring-donation behavior, and exactly one Draft status. Missing/placeholder source, semantic-marker comments, invalid evidence, or partial validation never become completion.

## Leases, correction, and deployment

PostgreSQL leases acquire the complete sorted component set atomically. A fencing token is required for renewal, baseline persistence, correction, validation, approval, and deployment. The exact-org baseline is an immutable Git commit captured before generated bytes are written. Org, lease, baseline, source, package, commit, plan, scope, inspection, validation, and approval bindings are rechecked immediately before side effects.

Only trusted structured validation codes authorize mechanical correction. The owner receives bounded context, the full set passes Task 9 again, and correction stops after three cycles. Material findings return to clarification/replanning; infrastructure findings consume no correction authority.

The guarded deployer requires successful current Salesforce validation, a clean worktree, current lease, exact hashes, unexpired separate approval, verified same org, and every Flow at Draft. It atomically reserves execution, uses the validation identity for the exact artifact, is idempotent after persisted success, and requires reconciliation after uncertain outcomes. It never activates Flow; success records `activated: false`.

## Persistence and secrets

API and worker share PostgreSQL; Redis delivers work and PostgreSQL retains the durable outbox. Production has no in-memory JobStore or inline queue fallback. Public projections omit prompts, and logs/errors redact credentials. Keep bearer tokens, External Credential principals, Salesforce auth, Jira credentials, and tunnel credentials in secret stores—never Git or command output.

`JIRA_ENABLED=false` is the default. Direct chat creates no Jira authority. If optional legacy Jira support is enabled, webhook HMAC/project/actor checks are additional gates and Jira text stays untrusted.

Phase 1 does not authorize Flow activation, unrestricted data mutation, arbitrary commands, default-org use, live production rollout, or autonomous Phase 2 behavior.
